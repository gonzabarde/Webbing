M8.6 — PRODUCTION REVIEW ENGINE (v2.7)
=======================================

OPERATIONAL HEADER
------------------
WHEN:     Ejecución — después de M9.8, ANTES de GATE 3 (obligatorio).
INPUTS:   M4-M5.5 aprobados, build en staging, QA M8.5, Frontend_Craft_Standard.md.
OUTPUT:   Tabla fidelidad (5 dims) + cross-browser + veredicto PASA/AJUSTES/FALLA.
GATES:    GATE 3 — FALLA si PERDIDO, drift CRÍTICO (3+ tells IA), o QA crítico.
FAIL:     PASA sin cross-browser; sin checklist tells; FALLA sin destino.
DEEP:     Leer destinos por dimensión y ejemplos de clichés por categoría.
REF:      Frontend_Craft_Standard.md §4 (ANTI-AI-SLOP CHECKLIST).

OBJETIVO
--------
Revisar el build producido y verificar si conserva la dirección creativa aprobada.
Este módulo evita que la implementación mate la idea.
El veredicto final requiere revisión en múltiples browsers.

INPUTS
------
OBLIGATORIOS:
- Concepto aprobado (M4)
- Percepción objetivo (M4.5)
- Visual Direction (M5)
- Signature System (M5)
- Mapa de Clichés de la categoría (M5.5)
- Build final desplegado en staging
- QA report (M8.5)
- Frontend Craft Standard (Frontend_Craft_Standard.md — checklist §4)

OPCIONALES:
- Mockups o maquetas originales (para comparación side-by-side)
- Feedback del cliente
- Versiones previas

PROCESO CLAUDE
--------------
1. Completar la tabla de fidelidad (ver formato abajo).
   Evaluar las 4 dimensiones y el drift genérico en simultáneo,
   no como pasos separados.

2. Verificar cross-browser.
   Chrome, Safari/WebKit y Firefox son obligatorios.
   Ver GATE DE CROSS-BROWSER abajo.

3. Verificar drift genérico — CHECKLIST DURO (dos capas, ambas obligatorias):
   a) Clichés de CATEGORÍA: comparar contra el Mapa de Clichés de M5.5
      (como hasta ahora). Si la categoría no tiene mapa, esta capa se omite
      declarándolo — la capa b) NUNCA se omite.
   b) Tells de IA: correr el ANTI-AI-SLOP CHECKLIST completo
      (Frontend_Craft_Standard.md §4, tells 1-12) sobre el build REAL
      (screenshot/staging, no la intención). Registrar el puntaje.

4. Integrar el QA report de M8.5.
   ¿Hay problemas críticos sin resolver?
   Si sí: el veredicto no puede ser PASA.

5. Emitir el veredicto final con destino si aplica.

TABLA DE FIDELIDAD — FORMATO
------------------------------
Dimensión          | Estado              | Nota
-------------------|---------------------|-----
Concept Fidelity   | OK / DRIFT / PERDIDO |
Perception Fidelity| OK / DRIFT / PERDIDO |
Direction Fidelity | OK / DRIFT / PERDIDO |
Signature Fidelity | OK / DRIFT / PERDIDO |
Generic Drift      | AUSENTE / LEVE / CRÍTICO |

Definiciones:
OK: la dimensión está intacta en el build.
DRIFT: la dimensión se desplazó parcialmente pero la intención se puede recuperar
       con ajustes menores.
PERDIDO: la dimensión no está presente en el build. Requiere corrección mayor.

SINCRONIZACIÓN DE FUENTE DE VERDAD (v2.3, de la corrida Vera) — condición
adicional para marcar Direction Fidelity o Signature Fidelity como OK:
Si durante la ejecución (M6-M9) una decisión de M3/M5 cambió por una razón
técnica real de build (ej. una fuente no está disponible en el proveedor
elegido), NO alcanza con que el build sea coherente en sí mismo — el
documento de origen (M3/M5) tiene que reflejar el valor real Y la razón del
cambio, sin tokens viejos sueltos. Antes de marcar Direction/Signature
Fidelity como OK: correr un grep del valor original (el que M3/M5 tenían
ANTES del cambio conocido) contra el propio documento de origen — cero
coincidencias esperadas. Si aparece el token viejo: Direction Fidelity es
DRIFT como mínimo, no OK, aunque el BUILD esté perfecto — el problema es que
la fuente de verdad quedó mintiendo, no que el sitio se vea mal. Loguear un
incidente sobre el cambio NO sustituye actualizar el documento de origen.

VERIFICACIÓN DE SOURCING FOTOGRÁFICO (v2.4, pregunta humana 2026-07-11) —
segunda condición adicional para marcar Direction Fidelity como OK: revisar
la Decisión de Sourcing Fotográfico de M0 (§7.1) y verificar EJECUTANDO
(mirando el build real, no la intención) que se cumplió. Precedente real:
CUORE y Vera pasaron con bloques de color sólido en vez de fotografía real
donde M5 definió sistema de imágenes — nadie lo verificó hasta que un
humano miró el deploy.
- Si la ruta elegida en M0 fue "cliente provee", "stock licenciado",
  "generado con IA" o "fotógrafo profesional": el build DEBE tener
  fotografía real cumpliendo la spec de M5 (estilo/luz/grading). Un bloque
  de color, un ph genérico o un placeholder = Direction Fidelity DRIFT como
  mínimo, sin importar qué tan bien esté el resto del build.
- Si la ruta fue "solo práctica": Pinterest como fuente directa de archivo
  es válido para esta ruta (decisión explícita del humano, M0 §7.1e) — pero
  NUNCA un placeholder de color puro en un build que pasa por GATE 3. Si el
  proyecto se reconvierte en cliente real, verificar que las imágenes de
  Pinterest ya se reemplazaron por (a)-(d) antes de GATE 4 — bloqueante.
- Si M0 no dejó una Decisión de Sourcing registrada: eso ya es FAIL CONDITION
  de M0 (§7.1) — señalarlo como hallazgo de M14, no improvisar una decisión
  acá con el proyecto ya construido.

VERIFICACIÓN DE CONTRASTE POR ROL EN EL DOM REAL (v2.7, INC-5+INC-6 Cursor
Café) — tercera condición adicional para marcar Direction Fidelity como OK.
§2.4.5 del Craft Standard exige declarar el umbral por token — pero es una
regla de ESCRITURA, y en la corrida de Cursor Café falló TRES veces en una
sesión, la última después de haber sido escrita y citada en el mismo
archivo. Confiar en que quién escribe el CSS se acuerde del umbral de cada
uso NO FUNCIONA — hace falta un verificador que corra sobre el DOM real, no
sobre la intención:
1. Para cada token de color usado en el build, detectar su ROL REAL por
   DÓNDE se aplica (no por lo que dice el comentario que lo declara): ¿es
   color de texto? ¿borde/outline de un control interactivo? ¿fill/stroke
   de un SVG que comunica contenido?
2. CRITERIO DE "DECORATIVO" (corregido, INC-6): NO usar `aria-hidden` como
   proxy de decorativo — son cosas distintas. `aria-hidden` significa "no lo
   anuncies al lector de pantalla" (correcto junto a un equivalente
   `sr-only`, es buena práctica de a11y); NO significa "sin información
   visual". Un SVG puede tener equivalente textual perfecto para ceguera Y
   ser crítico de contraste para baja visión — las dos cosas son ejes de
   accesibilidad distintos, no sustitutos. Test real de decorativo: ¿SI SE
   BORRA, el usuario pierde información? Si sí, se mide, tenga o no
   `aria-hidden`. Solo se excluye lo genuinamente ornamental (textura de
   fondo, línea puramente estética sin contenido).
3. Medir el contraste real de ese uso contra su fondo real renderizado.
4. Comparar contra el umbral que corresponde a ESE rol (texto 4.5 / texto
   grande o gráfico o límite de componente 3.0) — no contra el umbral con el
   que el token se declaró originalmente en M5.
5. REPORTE OBLIGATORIO DE COBERTURA (INC-6): el output SIEMPRE declara
   cuántos elementos se revisaron por rol ("texto: 12 revisados, 0 fallos";
   "SVG no-decorativo: 2 revisados, 0 fallos"), nunca solo la lista de
   fallos. "0 fallos" sin conteo de revisados es indistinguible de "el
   verificador no revisó nada" — verde falso silencioso. Si el conteo de
   revisados en alguna categoría esperada da 0 (ej. hay SVG en el build
   pero "SVG revisados: 0"), tratarlo como FALLA del verificador mismo, no
   como "nada que reportar".
Un token puede pasar la declaración de M5 y fallar acá si se reutilizó en un
rol distinto al declarado — ESO es lo que hay que agarrar, y es exactamente
lo que §2.4.5 sola no puede agarrar. Costo 1 (script reusable, corre sobre
clases/estilos computados reales). Sin este chequeo, Direction Fidelity no
puede marcarse OK aunque la tabla de M5 esté impecable en el papel.

DEFINICIÓN DE GENÉRICO
------------------------
Para detectar drift genérico, comparar el build contra el Mapa de Clichés
de M5.5 de la categoría del proyecto.

Ejemplos:
- SaaS con gradiente morado + mockup de dashboard en el hero →
  CRÍTICO. Son exactamente los dos primeros clichés del mapa.
- Clínica con hero de mujer en blanco + serif Canela + paleta rosa →
  CRÍTICO. Clichés 1, 2 y 3 del mapa.
- Portfolio con dark mode + cursor custom + palabra grande animada →
  CRÍTICO. Los tres primeros clichés del mapa de estudio creativo.

CAPA 1 — CLICHÉS DE CATEGORÍA (M5.5):
Si el build replica 2 o más clichés de la categoría: drift genérico CRÍTICO.
Si replica 1: drift genérico LEVE.
Si no replica ninguno: AUSENTE (en esta capa).

CAPA 2 — TELLS DE IA (Frontend_Craft_Standard.md §4) [v2.1]:
Si el build acumula 3+ tells del checklist: drift genérico CRÍTICO,
  aunque no replique ningún cliché de categoría. El build huele a IA.
Si acumula 1-2 tells: drift genérico LEVE como mínimo (no puede ser AUSENTE).
Si acumula 0: la capa 2 no modifica el resultado de la capa 1.
El resultado final de Generic Drift es el PEOR de las dos capas.
Además, verificar el piso técnico del estándar (AA, responsive 375px,
prefers-reduced-motion, focus visible): cualquier ausencia es problema
CRÍTICO de QA — bloquea el veredicto PASA por la vía del QA report.

VEREDICTO FINAL
----------------
PASA
  Todos los campos de la tabla son OK o DRIFT leve.
  No hay problemas críticos del QA report sin resolver.
  Pasa el check cross-browser.
  Drift genérico ausente o leve.

PASA CON AJUSTES
  1-2 campos en DRIFT. Los ajustes son menores (no requieren volver a un módulo).
  Los problemas del QA están resueltos excepto algunos "importantes" documentados.
  Pasa cross-browser.
  Drift genérico leve.

FALLA
  Cualquier campo en PERDIDO.
  Problemas críticos del QA sin resolver.
  Falla cross-browser.
  Drift genérico CRÍTICO.
  (El drift CRÍTICO puede venir de la capa de categoría O de la capa de
  tells de IA: 3+ tells del ANTI-AI-SLOP CHECKLIST = FALLA, sin excepción.
  GATE 3 no puede pasar sobre este veredicto — SKILL.md §6.)

DESTINOS EN CASO DE FALLA [obligatorios]
------------------------------------------
Si la dimensión falla, volver al módulo de origen:

Concept Fidelity PERDIDO → volver a M4 Concept Generation Engine.
  El build no tiene concepto. El concepto original no sobrevivió la implementación.

Perception Fidelity PERDIDO → volver a M4.5 Perception Engine.
  La emoción objetivo se perdió. Revisar la tabla de traducción percepción → decisión.

Direction Fidelity PERDIDO → volver a M5 Visual Direction System.
  El sistema visual no está presente. Color, tipografía o composición se perdieron.

Signature Fidelity PERDIDO → volver a M5, sección Signature System.
  La firma visual no es reconocible. Ajustar la implementación de la firma.

Generic Drift CRÍTICO → volver a M5.5 Visual Innovation Engine.
  El build se convirtió en una plantilla de la categoría.
  Necesita una desviación real en al menos una variable.
  Si el CRÍTICO vino de la capa de tells de IA con la dirección de M5/M5.5
  intacta en papel: el problema es de ejecución, no de dirección — corregir
  en el build contra el checklist §4 y re-correr M8.6 (no reabrir M5.5).
  Si la dirección misma era tibia (sin nombre, sin extremo): volver a M5
  paso 0 (dirección nombrada) y de ahí a M5.5.

DRIFT sin PERDIDO → no volver a un módulo anterior.
  Ajustar directamente en el build. Documentar los cambios realizados.

GATE DE CROSS-BROWSER [obligatorio antes del veredicto final]
--------------------------------------------------------------
Verificar el build en los tres browsers en este orden:
1. Chrome (versión actual)
2. Safari / WebKit (probar en Safari desktop o iOS Safari real si es posible)
3. Firefox (versión actual)

Check mínimo por browser:
- Layout no roto
- Tipografía renderiza correctamente
- Animaciones funcionan o degradan correctamente
- Formularios y CTAs operativos
- No hay overflow no intencional

Problemas comunes en Safari/WebKit a verificar específicamente:
- CSS grid gap con fracciones (puede calcular diferente)
- Animaciones con position: sticky
- backdrop-filter: blur() (requiere -webkit- prefix)
- Algunas propiedades de CSS variables en Safari antiguo
- Video autoplay sin muted: false en iOS

Si cualquier browser presenta problemas: FALLA.
No emitir veredicto PASA hasta que cross-browser esté limpio.

DIFERIMIENTO POR TOOLING (v2.2 — de la corrida ECOS):
Si el entorno solo ofrece UN motor (ej. solo Chromium, sin Safari/WebKit ni Firefox
disponibles), el cross-browser NO se puede ejecutar. En ese caso:
- NO falsificar un PASA de cross-browser que no se corrió (Principio de honestidad).
- NO hacer un downgrade silencioso ni dar el gate por cumplido.
- El veredicto correcto es PASA CON AJUSTES (si todo lo demás está OK), con el
  cross-browser cargado como BLOQUEANTE EXPLÍCITO de pre-deploy (GATE 4): el gate se
  difiere, no se salta. Registrar en el output qué motor se verificó y cuáles quedan
  pendientes, más los riesgos conocidos a chequear en ellos (ej. color-mix, backdrop-
  filter, render de fuentes variables).
Un motor único NO habilita un PASA limpio; habilita un diferimiento honesto y trazable.

MÉTODO DE VERIFICACIÓN — CUANDO EL SCREENSHOT FALLA O EL TIMELINE ESTÁ
CONGELADO (v2.5, INC-3 Cursor Café; screenshot-timeout ya es 3ª ocurrencia
del patrón Runa-P10):
Dos fallas distintas del mismo problema — verificar el build REAL sin
confiar en lo que el preview MUESTRA:
1. Screenshot con timeout consistente en ciertas páginas/estados: sustituir
   por eval + inspect (bounding boxes, estilos computados, geometría) sobre
   el DOM real. No es una pérdida de rigor — es otro método para la misma
   verificación.
2. Preview con `document.visibilityState: "hidden"` congela
   `document.timeline.currentTime` en 0 — las animaciones figuran como
   `running` pero nunca avanzan. Consecuencia real: "no vi la animación
   correr" NUNCA es evidencia de que esté rota, y un `getComputedStyle`
   ingenuo sobre un elemento animado puede devolver el estado `from`
   (`animation-fill-mode: backwards`) — que se lee como "el reveal está
   roto" cuando en realidad es el timeline el que está parado (falso
   positivo de la clase Vera-P2, en la dirección opuesta).
   Técnica correcta:
   - Para ver el estado FINAL real: `document.getAnimations().forEach(a =>
     a.finish())` antes de leer estilos/geometría.
   - Para el chequeo de Vera-P2 (¿el contenido es visible SIN motor de
     animación?): clonar el nodo con `style.animation = 'none'` y leer SU
     estado computado — prueba directa de que el fallback funciona, no una
     inferencia sobre el nodo animado original.
   Documentar en el output qué técnica se usó cuando el timeline esté
   congelado — para que quién audite después no repita el falso positivo.
3. Trampa de geometría SVG: un test ingenuo de "¿está visible?" con
   `rect.width > 0 && rect.height > 0` da FALSO NEGATIVO sobre una línea
   vertical/horizontal (`x1===x2` o `y1===y2` → bounding box de ancho/alto
   cero por definición; el grosor lo aporta el `stroke`, no el bbox). Test
   correcto para geometría SVG animada: `height > 0 && visibility ===
   'visible' && opacity !== '0' && strokeDashoffset === '0px'` — no solo
   dimensiones del bounding box.

TESTS
-----
- ¿La tabla de fidelidad tiene los 5 campos completados?
- ¿El drift genérico fue verificado contra M5.5 Y el checklist de tells?
- ¿El QA report de M8.5 fue integrado al veredicto?
- ¿Cross-browser fue verificado en Chrome, Safari y Firefox?

- ¿Si el veredicto es PASA CON AJUSTES, los ajustes están documentados?
- Si hubo un cambio conocido de M3/M5 durante la ejecución: ¿se grepeó el

OUTPUT
------
Tabla de fidelidad completa
Resultado del check cross-browser (browser por browser)
Resultado de drift genérico (capa categoría + puntaje tells IA)
Estado del QA report (críticos resueltos / pendientes)
Veredicto final: PASA / PASA CON AJUSTES / FALLA
Si FALLA: módulo de destino + razón de una línea por cada dimensión perdida
Si PASA CON AJUSTES: lista de ajustes con descripción concreta

FAIL CONDITIONS
---------------
- El build cambió la idea sin registro de por qué.
- La percepción objetivo no está presente en ninguna sección.
- La firma visual no se reconoce sin el logo.
- El build replica 2 o más clichés de la categoría.
- El build acumula 3+ tells del ANTI-AI-SLOP CHECKLIST.
- Hay problemas críticos del QA sin resolver.
- El veredicto es PASA sin haber hecho cross-browser.
- FALLA sin destino específico.
- El veredicto se emitió sin correr el ANTI-AI-SLOP CHECKLIST sobre el
  build real, o sin registrar el puntaje de tells.
- Direction/Signature Fidelity marcada OK sin correr el grep de tokens viejos
  contra el documento de origen (M3/M5), cuando hubo un cambio conocido
  durante la ejecución.
- Direction Fidelity marcada OK con placeholders/bloques de color donde la
  Decisión de Sourcing Fotográfico de M0 (§7.1) exigía fotografía real, sin
  marcarlo explícitamente como bloqueante de GATE 4.
