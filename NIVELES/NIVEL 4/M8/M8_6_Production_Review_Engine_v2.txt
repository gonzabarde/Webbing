M8.6 — PRODUCTION REVIEW ENGINE (v2.13)
=======================================

OPERATIONAL HEADER
------------------
WHEN:     Ejecución — después de M9.8, ANTES de GATE 3 (obligatorio).
INPUTS:   M4-M5.5 aprobados, build en staging, QA M8.5, Frontend_Craft_Standard.md.
OUTPUT:   Tabla fidelidad (5 dims) + cross-browser + veredicto PASA/AJUSTES/FALLA.
GATES:    GATE 3 — FALLA si PERDIDO, drift CRÍTICO (3+ tells IA), o QA crítico.

DEEP:     Leer destinos por dimensión y ejemplos de clichés por categoría.

Revisar el build producido y verificar si conserva la dirección creativa aprobada.
Este módulo evita que la implementación mate la idea.
El veredicto final requiere revisión en múltiples browsers.

PROCESO CLAUDE
--------------
1. Completar la tabla de fidelidad (ver formato abajo).
   Evaluar las 4 dimensiones y el drift genérico en simultáneo,
   no como pasos separados.

2. Verificar cross-browser.
   Chrome, Safari/WebKit y Firefox son obligatorios.
   Ver GATE DE CROSS-BROWSER abajo.

3. Verificar drift genérico — CHECKLIST DURO (dos capas, ambas obligatorias):
   a) Clichés de CATEGORÍA: comparar contra el Mapa de Clichés de M5.5
      (como hasta ahora). Si la categoría no tiene mapa, esta capa se omite
      declarándolo — la capa b) NUNCA se omite.
   b) Tells de IA: correr el ANTI-AI-SLOP CHECKLIST completo
      (Frontend_Craft_Standard.md §4, tells 1-13) sobre el build REAL
      (screenshot/staging, no la intención). Registrar el puntaje.

4. Integrar el QA report de M8.5.
   ¿Hay problemas críticos sin resolver?
   Si sí: el veredicto no puede ser PASA.

5. Emitir el veredicto final con destino si aplica.

TABLA DE FIDELIDAD — FORMATO
------------------------------
Dimensión          | Estado              | Nota
-------------------|---------------------|-----
Concept Fidelity   | OK / DRIFT / PERDIDO |
Perception Fidelity| OK / DRIFT / PERDIDO |
Direction Fidelity | OK / DRIFT / PERDIDO |
Signature Fidelity | OK / DRIFT / PERDIDO |
Generic Drift      | AUSENTE / LEVE / CRÍTICO |

Definiciones:
OK: la dimensión está intacta en el build.
DRIFT: la dimensión se desplazó parcialmente pero la intención se puede recuperar
       con ajustes menores.
PERDIDO: la dimensión no está presente en el build. Requiere corrección mayor.

SINCRONIZACIÓN DE FUENTE DE VERDAD (v2.3, de la corrida Vera) — condición
adicional para marcar Direction Fidelity o Signature Fidelity como OK:
Si durante la ejecución (M6-M9) una decisión de M3/M5 cambió por una razón
técnica real de build (ej. una fuente no está disponible en el proveedor
elegido), NO alcanza con que el build sea coherente en sí mismo — el
documento de origen (M3/M5) tiene que reflejar el valor real Y la razón del
cambio, sin tokens viejos sueltos. Antes de marcar Direction/Signature
Fidelity como OK: correr un grep del valor original (el que M3/M5 tenían
ANTES del cambio conocido) contra el propio documento de origen — cero
coincidencias esperadas. Si aparece el token viejo: Direction Fidelity es
DRIFT como mínimo, no OK, aunque el BUILD esté perfecto — el problema es que
la fuente de verdad quedó mintiendo, no que el sitio se vea mal. Loguear un
incidente sobre el cambio NO sustituye actualizar el documento de origen.

VERIFICACIÓN DE SOURCING FOTOGRÁFICO (v2.4, pregunta humana 2026-07-11) —
segunda condición adicional para marcar Direction Fidelity como OK: revisar

CUORE y Vera pasaron con bloques de color sólido en vez de fotografía real

  "generado con IA" o "fotógrafo profesional": el build DEBE tener
  fotografía real cumpliendo la spec de M5 (estilo/luz/grading). Un bloque
  de color, un ph genérico o un placeholder = Direction Fidelity DRIFT como

- Si la ruta fue "solo práctica": Pinterest como fuente directa de archivo
  es válido para esta ruta (decisión explícita del humano, M0 §7.1e) — pero
  NUNCA un placeholder de color puro en un build que pasa por GATE 3. Si el
  proyecto se reconvierte en cliente real, verificar que las imágenes de
  Pinterest ya se reemplazaron por (a)-(d) antes de GATE 4 — bloqueante.
- Si M0 no dejó una Decisión de Sourcing registrada: eso ya es FAIL CONDITION
  de M0 (§7.1) — señalarlo como hallazgo de M14, no improvisar una decisión
  acá con el proyecto ya construido.

VERIFICACIÓN DE CONTRASTE POR ROL EN EL DOM REAL (v2.7, INC-5+INC-6 Cursor
Café) — tercera condición adicional para marcar Direction Fidelity como OK.
§2.4.5 del Craft Standard exige declarar el umbral por token — pero es una
regla de ESCRITURA, y en la corrida de Cursor Café falló TRES veces en una
sesión, la última después de haber sido escrita y citada en el mismo
archivo. Confiar en que quién escribe el CSS se acuerde del umbral de cada
uso NO FUNCIONA — hace falta un verificador que corra sobre el DOM real, no
sobre la intención:
1. Para cada token de color usado en el build, detectar su ROL REAL por
   DÓNDE se aplica (no por lo que dice el comentario que lo declara): ¿es
   color de texto? ¿borde/outline de un control interactivo? ¿fill/stroke
   de un SVG que comunica contenido?
2. CRITERIO DE "DECORATIVO" (corregido, INC-6): NO usar `aria-hidden` como
   proxy de decorativo — son cosas distintas. `aria-hidden` significa "no lo
   anuncies al lector de pantalla" (correcto junto a un equivalente
   `sr-only`, es buena práctica de a11y); NO significa "sin información
   visual". Un SVG puede tener equivalente textual perfecto para ceguera Y
   ser crítico de contraste para baja visión — las dos cosas son ejes de
   accesibilidad distintos, no sustitutos. Test real de decorativo: ¿SI SE
   BORRA, el usuario pierde información? Si sí, se mide, tenga o no
   `aria-hidden`. Solo se excluye lo genuinamente ornamental (textura de
   fondo, línea puramente estética sin contenido).
3. Medir el contraste real de ese uso contra su fondo real renderizado.
4. Comparar contra el umbral que corresponde a ESE rol (texto 4.5 / texto
   grande o gráfico o límite de componente 3.0) — no contra el umbral con el
   que el token se declaró originalmente en M5.
5. REPORTE OBLIGATORIO DE COBERTURA (INC-6): el output SIEMPRE declara
   cuántos elementos se revisaron por rol ("texto: 12 revisados, 0 fallos";
   "SVG no-decorativo: 2 revisados, 0 fallos"), nunca solo la lista de
   fallos. "0 fallos" sin conteo de revisados es indistinguible de "el
   verificador no revisó nada" — verde falso silencioso. Si el conteo de
   revisados en alguna categoría esperada da 0 (ej. hay SVG en el build
   pero "SVG revisados: 0"), tratarlo como FALLA del verificador mismo, no
   como "nada que reportar".
Un token puede pasar la declaración de M5 y fallar acá si se reutilizó en un
rol distinto al declarado — ESO es lo que hay que agarrar, y es exactamente
lo que §2.4.5 sola no puede agarrar. Costo 1 (script reusable, corre sobre
clases/estilos computados reales). Sin este chequeo, Direction Fidelity no
puede marcarse OK aunque la tabla de M5 esté impecable en el papel.

VERIFICACIÓN DE RELACIONES ESPACIALES EN EL DOM REAL (v2.9, P1 corrida
Estudio de Tatuaje) — CUARTA condición adicional para marcar Direction
Fidelity como OK. Cierra el punto ciego que la v2.8 abrió sin querer.
EL PROBLEMA: al declarar eval+inspect como MÉTODO PRIMARIO (v2.8, por la
limitación estructural del screenshot), el sistema perdió sin reemplazo lo
único que el screenshot verificaba gratis: la COMPOSICIÓN. eval+inspect mide
PROPIEDADES (contraste, tamaños, overflow horizontal, tells) pero no
RELACIONES ESPACIALES (¿dos elementos se pisan? ¿el texto respeta el margen
del sistema?). Mientras el screenshot era el método principal la ceguera no
importaba; al volverse primario eval+inspect, la ceguera pasa de puntual a
SISTEMÁTICA en todo proyecto futuro.
CASO REAL QUE LO MOTIVA (Estudio de Tatuaje, 2026-07-14): el hero pasó GATE 3
con el wordmark del header ENCIMADO sobre el eyebrow y todo el contenido
pegado al borde (x=0) — el `.hero` no tenía padding horizontal. Verificador
de contraste 61 elementos/0 fallos, 0/13 tells, AA y overflow: TODO verde.
Lo agarró el humano mirando una captura, en segundos. Ningún chequeo
automático lo vio porque ninguno miraba dónde está una caja respecto de otra.
QUÉ CORRER (costo 1, mismo eval, sobre el DOM real):
1. COLISIÓN: para pares de elementos que NO deben solaparse (header/nav vs.
   contenido del hero, texto vs. texto, label vs. label), medir intersección
   de `getBoundingClientRect()`. Dos rects que se cruzan y no son
   deliberadamente superpuestos (R3 declara la superposición intencional en
   M5) = FALLA.
2. ALINEACIÓN AL SISTEMA: los bloques de texto respetan el padding del
   sistema — `left` alineado al token de padding (ej. `var(--pad)`), NUNCA
   x=0 salvo BLEED DECLARADO en M5. Un texto a x=0 sin declaración es
   defecto, no asimetría: la asimetría intencional (R3) se declara y se
   verifica contra esa declaración.
3. SANGRADO INTENCIONAL: si M5 declara que un elemento sangra fuera del
   viewport (R3), verificar que sangra el ELEMENTO GRÁFICO y no el TEXTO —
   texto cortado por el borde es defecto (lección INC-4: el texto nunca
   cruza el borde).
REPORTE OBLIGATORIO (misma regla que la cobertura de v2.7): declarar cuántos
pares se chequearon y cuántas colisiones se encontraron. "0 colisiones" sin
conteo de pares es indistinguible de "no miré nada".
Sin este chequeo, Direction Fidelity NO puede marcarse OK: el sistema visual
puede estar impecable en tokens y estar roto en composición — y desde v2.8
no hay ningún otro mecanismo que lo agarre.

VERIFICACIÓN DE INTERACCIÓN REAL (v2.11, hallazgo P9 del re-pase SAVIA,
2026-07-17) — condición adicional para marcar Signature Fidelity como OK
cuando la firma documentada (M5/M9.8) es interactiva (hover, click, scroll-
trigger, flip, reveal). CASO REAL QUE LO MOTIVA: "El Giro" de SAVIA tenía el
CSS correcto (`rotateY(180deg)`, transición 0.32s) — M8.6 lo marcó PRESENTE
verificando que la regla existía en el DOM/CSS computado. Pero la firma
NUNCA se disparaba con una interacción real: `prefers-reduced-motion` la
congelaba con `!important`, el trigger era hover-only (muerto en mobile) y
no tenía affordance visible — nadie sabía que había algo para tocar. El
humano lo encontró abriendo el build en su propio navegador, no M8.6.
DIFERENCIA DE FONDO: verificar que una firma EXISTE en el código (propiedad
estática) no es lo mismo que verificar que se EXPERIMENTA (evento real).
Son la misma clase de hueco que la Verificación de Relaciones Espaciales de
v2.9 (mide propiedades, no lo que un usuario real encuentra).
QUÉ CORRER: para cada elemento con firma interactiva documentada:
1. Disparar el evento REAL (mouseenter/click/scroll-into-view según el
   trigger declarado) sobre un navegador real — nunca forzando el estado
   por JS/DOM directamente. Forzar el estado prueba que el CSS es capaz de
   producir el efecto; no prueba que un usuario lo va a encontrar.
2. Confirmar que existe una AFFORDANCE visible en estado de reposo (algo que
   indique "esto es interactivo") — sin affordáncia, una firma correcta en
   código sigue siendo una firma que nadie descubre.
3. Confirmar el comportamiento bajo `prefers-reduced-motion`: la información
   de la firma (no necesariamente el movimiento) tiene que seguir siendo
   accesible — una regla de reduced-motion mal escrita puede CONGELAR el
   contenido en vez de solo quitar la animación (exactamente lo que le pasó
   a SAVIA: el `!important` dejaba la tarjeta trabada de frente, sin acceso
   al reverso, para cualquiera con reduce-motion activo).
Sin este chequeo, Signature Fidelity NO puede marcarse OK para firmas
interactivas por más que el CSS/DOM estético esté impecable.

VERIFICACIÓN DE HIDRATACIÓN/INTERACTIVIDAD FUNCIONAL (v2.13, hallazgo H-1
Calibre, 2026-07-18) — GENERALIZA la Verificación de Interacción Real de
arriba de la FIRMA a CUALQUIER interactividad de cliente que el build
necesite para funcionar (formulario principal, CTA primario, cualquier
componente client-side crítico). Condición adicional para integrar el QA
report (paso 4) — un problema acá es CRÍTICO de QA, bloquea PASA.
CASO REAL QUE LO MOTIVA: en Calibre, un CSP estricto en dev (ver B3-SEC-5)
bloqueaba `eval()` y el cliente de React nunca hidrataba. La página pasó
TODOS los chequeos estáticos limpio — contraste, 13 tells, relaciones
espaciales — con el JavaScript del cliente completamente muerto. El
formulario de demo caía a un submit nativo GET (`/?name=...`) en vez de
llamar a su handler real. Sin error de consola visible. Lo agarró recién un
test que efectivamente ENVIÓ el formulario y miró la red — el mismo patrón
de v2.11 (existe ≠ se experimenta), esta vez no en la firma sino en TODA la
capa de interactividad del cliente.
QUÉ CORRER, sobre el build real, ANTES del veredicto:
1. Identificar el/los componente(s) client-side CRÍTICO(s) para el propósito
   del proyecto — casi siempre el formulario principal de conversión o el
   CTA primario (arquetipo #1/#2: el checkout o el form de demo/lead).
2. Disparar UN evento real de usuario sobre ese componente (submit con datos
   reales, click) — nunca asumir por la presencia de un `onSubmit` en el
   código que corre de verdad.
3. Confirmar en la red (no solo en el DOM) que el evento disparó lo que
   tenía que disparar: un `fetch`/XHR a la ruta esperada con el método
   esperado (POST a una API, no un GET nativo del navegador al mismo path).
   Un submit que navega a `?campo=valor` en vez de llamar a la API es la
   señal inequívoca de que el handler de React nunca se enganchó.
4. Si falla: es un problema de HIDRATACIÓN, no de UI — revisar CSP (B3-SEC-5),
   errores de consola silenciosos, o mismatch de SSR/CSR antes de tocar nada
   visual. El build puede estar perfecto en apariencia con el cliente muerto.
Sin este chequeo, ninguna Fidelity puede marcarse OK basándose solo en
verificaciones estáticas: todas (contraste, tells, espacial, sourcing)
asumen que el HTML/CSS renderizado es lo que el usuario experimenta, pero
ninguna prueba que el JavaScript del cliente esté vivo.

LECTURA EN FRÍO (v2.11, hallazgo P10 del re-pase SAVIA, 2026-07-17) — paso
obligatorio ANTES de emitir el veredicto final, cuando ambas capas de
Generic Drift (clíchés + tells) dieron verde. Razón: verificar fidelidad de
un build contra la spec que uno mismo (M4/M5) escribió es estructuralmente
autoconfirmatorio — Claude tiende a leer su propia intención en su propia
ejecución, aunque la ejecución haya sido tibia. Ninguna de las dos capas de
drift mide esto: una capa compara contra clichés de mercado, la otra contra
un checklist fijo — ninguna pregunta "¿esto se siente genuino?".
QUÉ HACER: mirar la captura real del build (hero + al menos una sección más)
SIN releer la spec de M4/M5 primero — como si fuera la primera vez que se ve
el proyecto. Escribir en UNA frase qué es memorable ("acá es donde este
proyecto se distingue de cualquier otro de su categoría: ___"). Si no sale
nada genuinamente nombrable en esa frase, es Generic Drift — sin importar que
el mapa de clichés y el checklist de tells hayan dado verde. Esta lectura no
reemplaza las dos capas cuantificadas; es una tercera verificación cualitativa
que no puede autoconfirmarse porque deliberadamente no consulta la intención
original antes de opinar.
Si la Lectura en Frío no encuentra nada memorable pero ambas capas
cuantificadas dieron verde: el veredicto no puede ser PASA limpio — como
mínimo PASA CON AJUSTES, documentando qué faltó hacer memorable y dónde
(hero, firma, momento del scroll).

DEFINICIÓN DE GENÉRICO
------------------------
Para detectar drift genérico, comparar el build contra el Mapa de Clichés
de M5.5 de la categoría del proyecto.

Ejemplos:
- SaaS con gradiente morado + mockup de dashboard en el hero →
  CRÍTICO. Son exactamente los dos primeros clichés del mapa.
- Clínica con hero de mujer en blanco + serif Canela + paleta rosa →
  CRÍTICO. Clichés 1, 2 y 3 del mapa.
- Portfolio con dark mode + cursor custom + palabra grande animada →
  CRÍTICO. Los tres primeros clichés del mapa de estudio creativo.

CAPA 1 — CLICHÉS DE CATEGORÍA (M5.5):
Si el build replica 2 o más clichés de la categoría: drift genérico CRÍTICO.
Si replica 1: drift genérico LEVE.
Si no replica ninguno: AUSENTE (en esta capa).

CAPA 2 — TELLS DE IA (Frontend_Craft_Standard.md §4) [v2.11 — REPORTE
OBLIGATORIO POR TELL, no un conteo agregado]:
Correr los 13 tells UNO POR UNO contra el build real (captura o DOM/CSS
computado), no contra la intención de M4/M5. Reportar cada uno con veredicto
PRESENTE/AUSENTE y una línea de evidencia — igual tratamiento que el reporte
de cobertura de contraste (v2.7) y de relaciones espaciales (v2.9): un número
agregado ("2/13 tells") sin la lista completa es indistinguible de "no lo
corrí", mismo verde falso silencioso. **Hallazgo del re-pase SAVIA
(2026-07-17): esta capa existía desde 2026-07-04 pero en la práctica solo se
corría la Capa 1 (clichés de M5.5, mercado) — el checklist de 13 tells se
salteaba en silencio porque nada exigía el reporte item por item.** Un
build puede tener cero clichés de categoría y seguir siendo genérico por
tells de IA (hero simétrico, cards uniformes, acento tímido) que el mapa de
M5.5 no cubre.
Si el build acumula 3+ tells del checklist: drift genérico CRÍTICO,
  aunque no replique ningún cliché de categoría. El build huele a IA.
Si acumula 1-2 tells: drift genérico LEVE como mínimo (no puede ser AUSENTE).
Si acumula 0: la capa 2 no modifica el resultado de la capa 1.
El resultado final de Generic Drift es el PEOR de las dos capas.
Además, verificar el piso técnico del estándar (AA, responsive 375px,
prefers-reduced-motion, focus visible): cualquier ausencia es problema
CRÍTICO de QA — bloquea el veredicto PASA por la vía del QA report.

VEREDICTO FINAL
----------------
PASA
  Todos los campos de la tabla son OK o DRIFT leve.
  No hay problemas críticos del QA report sin resolver.
  Pasa el check cross-browser.
  Drift genérico ausente o leve.

PASA CON AJUSTES
  1-2 campos en DRIFT. Los ajustes son menores (no requieren volver a un módulo).
  Los problemas del QA están resueltos excepto algunos "importantes" documentados.
  Pasa cross-browser.
  Drift genérico leve.

FALLA
  Cualquier campo en PERDIDO.
  Problemas críticos del QA sin resolver.
  Falla cross-browser.
  Drift genérico CRÍTICO.
  (El drift CRÍTICO puede venir de la capa de categoría O de la capa de
  tells de IA: 3+ tells del ANTI-AI-SLOP CHECKLIST = FALLA, sin excepción.
  GATE 3 no puede pasar sobre este veredicto — SKILL.md §6.)

DESTINOS EN CASO DE FALLA [obligatorios]
------------------------------------------
Si la dimensión falla, volver al módulo de origen:

Concept Fidelity PERDIDO → volver a M4 Concept Generation Engine.
  El build no tiene concepto. El concepto original no sobrevivió la implementación.

Perception Fidelity PERDIDO → volver a M4.5 Perception Engine.
  La emoción objetivo se perdió. Revisar la tabla de traducción percepción → decisión.

Direction Fidelity PERDIDO → volver a M5 Visual Direction System.
  El sistema visual no está presente. Color, tipografía o composición se perdieron.

Signature Fidelity PERDIDO → volver a M5, sección Signature System.
  La firma visual no es reconocible. Ajustar la implementación de la firma.

Generic Drift CRÍTICO → volver a M5.5 Visual Innovation Engine.
  El build se convirtió en una plantilla de la categoría.
  Necesita una desviación real en al menos una variable.
  Si el CRÍTICO vino de la capa de tells de IA con la dirección de M5/M5.5
  intacta en papel: el problema es de ejecución, no de dirección — corregir
  en el build contra el checklist §4 y re-correr M8.6 (no reabrir M5.5).
  Si la dirección misma era tibia (sin nombre, sin extremo): volver a M5
  paso 0 (dirección nombrada) y de ahí a M5.5.

DRIFT sin PERDIDO → no volver a un módulo anterior.
  Ajustar directamente en el build. Documentar los cambios realizados.

GATE DE CROSS-BROWSER [obligatorio antes del veredicto final]
--------------------------------------------------------------
Verificar el build en los tres browsers en este orden:
1. Chrome (versión actual)
2. Safari / WebKit (probar en Safari desktop o iOS Safari real si es posible)
3. Firefox (versión actual)

Check mínimo por browser:
- Layout no roto
- Tipografía renderiza correctamente
- Animaciones funcionan o degradan correctamente
- Formularios y CTAs operativos
- No hay overflow no intencional

Problemas comunes en Safari/WebKit a verificar específicamente:
- CSS grid gap con fracciones (puede calcular diferente)
- Animaciones con position: sticky
- backdrop-filter: blur() (requiere -webkit- prefix)
- Algunas propiedades de CSS variables en Safari antiguo
- Video autoplay sin muted: false en iOS

Si cualquier browser presenta problemas: FALLA.

MÉTODO DE VERIFICACIÓN — CAPTURA DE PANTALLA DEL PANEL DE PREVIEW (v2.8,
INC-2 Estudio de Tatuaje, causa raíz diagnosticada tras 5 ocurrencias del
patrón Runa-P10):
EL SCREENSHOT DEL PANEL DE PREVIEW NO ES UN MÉTODO CONFIABLE — no es "falla
a veces", es una limitación estructural del entorno. Diagnóstico por
experimento controlado (no teoría): una página TRIVIAL (blanca, sin
contenido del proyecto) también cuelga — descarta el código del proyecto
como causa. El tab del panel nunca es la superficie en foreground
(`document.hidden`, `document.hasFocus()===false`), y `requestAnimationFrame`
dispara 0 frames — el compositor de Chrome no pinta un tab oculto.
`Page.captureScreenshot` (CDP) espera un frame compositeado que nunca
llega y cuelga hasta el timeout. Por eso `eval`/`inspect`/`read_page`
funcionan (usan dominios DOM/Runtime de CDP, no necesitan compositor) y el
screenshot no.
CONSECUENCIA PRÁCTICA — cambia el orden de método, no solo agrega un
fallback:
1. **eval + inspect + clon es el MÉTODO PRIMARIO** de verificación de build,
   no un sustituto de última instancia. No intentar screenshot del panel
   primero "por las dudas" — arrancar directo por acá.
2. Si hace falta una IMAGEN REAL (para que un humano la revise visualmente,
   no para verificar el build): dos vías posibles según qué entorno esté
   corriendo M8.6 — elegir la que aplique, no asumir que la primera
   siempre está disponible:
   a) Si M8.6 corre en el chat, con el navegador del humano conectado
      (herramienta tipo `claude-in-chrome`): capturar por ahí, con el
      server de preview vivo. El Chrome real pinta de verdad porque es una
      ventana real, no un tab offscreen. Requisitos: confirmar que el
      server de preview sigue arriba antes de capturar (se reapean solos);
      usar `http://localhost:<puerto>` con el server levantado, nunca
      `file://`.
   b) Si M8.6 corre en un entorno sin acceso a ese Chrome (típicamente Claude
      Code u otro sandbox separado del navegador del humano, donde
      `http://localhost` del dev server no resuelve porque no hay red
      compartida con el navegador que sí lo alcanza): capturar vía Chromium
      headless (Playwright/Puppeteer) corriendo en el MISMO entorno/host que
      el server de preview — ahí sí hay red compartida. Guardar como PNG y
      leer con la tool de imágenes. Cubre desktop y 375px (mismo binario, dos
      viewports) en la misma corrida.

      caído (confirmado con curl, no con teoría de red — ver
      INCIDENTES_M14.md H-5, retractado como FALSE CERTAINTY). El método en
      sí sigue siendo válido para su caso real (entornos sin conector al
      navegador del humano, que sí existen) — se mantiene por mérito propio,
      no por el incidente que lo motivó a escribirse.
   Ninguna de las dos vías es opcional "si se puede" — alguna de las dos
   tiene que estar disponible en cualquier entorno donde M8.6 corra, o la
   Lectura en Fría (v2.11) queda estructuralmente sin poder cerrarse.
3. El fix de raíz (`Page.captureScreenshot` con `fromSurface:false`, o
   `Page.bringToFront` + focus emulation antes de capturar) vive en la
   implementación de la tool de screenshot del panel — fuera del alcance
   de un proyecto individual. Si el harness lo expone, resolvería la clase
   entera de una vez.

Otras dos fallas relacionadas, mismo método primario las resuelve:
1. Preview con `document.visibilityState: "hidden"` congela
   `document.timeline.currentTime` en 0 — las animaciones figuran como
   `running` pero nunca avanzan. "No vi la animación correr" NUNCA es
   evidencia de que esté rota, y un `getComputedStyle` ingenuo sobre un
   elemento animado puede devolver el estado `from`
   (`animation-fill-mode: backwards`) — falso positivo de la clase
   Vera-P2, en dirección opuesta.
   Técnica correcta:
   - Para ver el estado FINAL real: `document.getAnimations().forEach(a =>
     a.finish())` antes de leer estilos/geometría.
   - Para el chequeo de Vera-P2 (¿el contenido es visible SIN motor de
     animación?): clonar el nodo con `style.animation = 'none'` y leer SU
     estado computado — prueba directa de que el fallback funciona, no una
     inferencia sobre el nodo animado original.
2. Trampa de geometría SVG: un test ingenuo de "¿está visible?" con
   `rect.width > 0 && rect.height > 0` da FALSO NEGATIVO sobre una línea
   vertical/horizontal (`x1===x2` o `y1===y2` → bounding box de ancho/alto
   cero por definición; el grosor lo aporta el `stroke`, no el bbox). Test
   correcto para geometría SVG animada: `height > 0 && visibility ===
   'visible' && opacity !== '0' && strokeDashoffset === '0px'` — no solo
   dimensiones del bounding box.
Documentar en el output qué técnica se usó en cada caso — para que quién
audite después no repita el falso positivo ni pierda tiempo reintentando un
screenshot de panel que estructuralmente no va a funcionar.
